# Как работаем над задачами

## Дисциплина изменений

- В изменениях — **только то, что относится к задаче**. Не подчищать «заодно» чужой код,
  форматирование, соседние TODO.
- Не создавать в репозитории вспомогательные файлы: заметки, черновики, временные скрипты,
  отчёты. Временное — в scratchpad.
- Чужие локальные изменения в рабочей копии (настройки разработчика, lock-файлы и т.п.) не
  трогать и в коммит не включать. Перед коммитом — явный список файлов.
- Генерированный код: после регенерации оставлять только файлы, изменившиеся из-за моей правки.
- Коммитит пользователь сам, если не сказано иное. Сообщение — короткое, в стиле проекта.
- Ветки тоже создаёт пользователь: назвать ветку и от чего её делать, дождаться «сделал».
- **Секреты не читать** — ни `cat`, ни `grep`: `~/.gradle/gradle.properties`, `~/.npmrc`, `~/.ssh/*`,
  `.credentials*`, `.env`. Наличие проверять `test -f`, значение переменной — не печатать.
  SSH-доступ (`ssh -T`) не проверять — пользователь делает это сам. Скопировать файл с секретами
  (в WSL-профиль и т.п.) — дать пользователю команду для `!`.
- **Меньше запросов разрешений.** Файлы править через Edit/Write (заметки, `CLAUDE.md`, `.claude/**`,
  `claude-config` разрешены без запроса в `~/.claude/settings.json`), а не через `python3`/`sed -i`/heredoc в
  Bash — каждая такая Bash-команда спрашивает разрешение. Edit сохраняет CRLF. Чтение — простыми
  командами из разрешённого списка (`git status/log/diff/show`, `ls`, `grep`, `head`, `tail`, `sed -n`),
  не склеивать их в длинные цепочки с `cd`, `export`, `python3 -c` — цепочка тоже спросит.
- **Разрушительные шаги** (удаление, перезапись, `rm`, `git rm`, переустановка зависимостей, запуск
  скриптов, которые меняют файлы) — отдельными командами, не цепочкой `&&` с другими действиями;
  после каждого — проверить результат, и только потом следующий шаг. Перед ними — посмотреть цель
  (`git status`, `ls`, `--dry-run`).

## Договорённости — в файлы

Всё, что я прошу запомнить, записывать сразу в файл. Какой файл и где лежит — `structure.md`.

Отдельно: решили проблему проекта (как правильно запускать тесты, почему сделано «через одно
место», обходной путь) — сами или я подсказал — сразу в `<repo>/.claude/gotchas.md`. Если грабля не про проект, а общая (WSL, инструмент,
библиотека) — в `~/.claude/personal/gotchas.md`.

## Документ по задаче

`<repo>` — репозиторий, **где меняется код задачи**, а не тот, где запущена сессия (фронтовая задача →
документ во фронте, даже если сессия открыта в бэке). Код меняется в нескольких репозиториях (бэк и фронт) —
документ **в каждом**: суть задачи и общие решения в обоих, «что сделано» / «как проверить» / коммиты — про
изменения именно этого репозитория; в «Пересечениях» — ссылка на документ в соседнем.

На каждую задачу — `<repo>/.claude/tickets/<KEY>.md`, завести **в начале** (копией шаблона
`~/.claude/personal/templates/ticket.md`) и дописывать по ходу. Порядок работы над тикетом —
скилл `/ticket`; проектные параметры для него (трекер, токен, ветка, стиль коммита, особенности
шагов, калибровка оценок) — раздел «Задачи» в `<repo>/CLAUDE.md`. Сам документ — про проект и
остаётся в проекте; шаблон и порядок — мои настройки. В документе:

- суть задачи и где истина (тикет, комментарии, вложения, wiki); перевод, если не по-русски;
- коммиты — какой пункт закрывает каждый;
- что сделано по пунктам, со ссылками `файл:строка`;
- **принятые решения и почему**, как откатить;
- сознательно оставленные шероховатости;
- пересечения с другими задачами и соседними репозиториями;
- оценка (скилл `/estimate`), как проверить, грабли.

Грабли не про задачу, а про проект вообще — переносить в `<repo>/.claude/gotchas.md`; если не про
проект, а общие (инструмент, ОС, библиотека) — в `~/.claude/personal/gotchas.md`.

## Запись по теме без тикета

Отдельная тема, у которой нет тикета (исследование, настройка окружения, договорённости о
процессе, разбор чужого кода), — такой же документ, только ключ — дата и тема:

```
<repo>/.claude/tickets/<YYYY-MM-DD>-<тема>.md     # например 2026-09-25-claude-settings.md
```

Та же папка, что у тикетов, — чтобы всё про ход работы лежало в одном месте. Содержание — по тем
же пунктам, насколько применимо: суть, что сделано и где, решения и почему, открытые вопросы.
Если тема не про конкретный репозиторий (например, общие настройки ассистента) — записи не
нужно, итог фиксируется в самих файлах `~/.claude/personal/`.

Мелкий вопрос в рамках текущего тикета — не новая тема: дописывать в документ тикета.

## Проверка

- Тесты: сначала точечно, потом полный прогон; сборка. Если новый тест не попал в запуск (белые
  списки, фильтры) — убедиться, что число тестов выросло.
- Для UI-изменений — дать мне пошаговый сценарий ручной проверки: что нажать, какой запрос
  увидеть в Network, какой ответ ожидать.
