# CODE — общее для любого кода

Проверить, когда код задачи написан, до отдачи на коммит (`/review-lessons`). Технология — свой файл в `tech/`.

## CODE.RULE — как писать

- **CODE.RULE.1** **Где живёт код.** Логика для сущности из внутренней библиотеки (общий `core`/`common`-модуль) — там
  же, где у соседних сущностей такая же логика. Посмотреть ближайший аналог: если у него фильтр/репозиторий/сервис в
  библиотеке — новый тоже туда, а не в приложение. Нет доступа к библиотеке — сказать об этом заранее, а не после
  ревью. **Делать как у аналога один в один:** та же сигнатура (типы параметров — из библиотеки/фреймворка, а не классы
  приложения, иначе в библиотеку не перенести), те же проверки входа, то же место. Перед сдачей — положить свой метод
  рядом с методом аналога и сравнить построчно.
- **CODE.RULE.2** **Каждая неочевидная строка — либо доказана, либо убрана.** Явная настройка, которая «кажется нужной»
  (явный маппинг поля, лишняя аннотация, защитная проверка), — проверить экспериментом: убрать → собрать → посмотреть
  результат. Не подтвердилось — не добавлять. Ответ ревьюеру «на всякий случай» не годится. Что осталось — в
  «Неочевидное в коде» (`WORK.DONE.2`).
- **CODE.RULE.3** **Выбор API/подхода, по которому в проекте нет стандарта** (например, `nanoTime` vs
  `currentTimeMillis`) — иметь готовый ответ: где в проекте сделано так же + ссылка на первоисточник (документация,
  исходники).
- **CODE.RULE.4** **Импорты — только поимённые, без `*`**, в любом языке и из любого пакета (свой код, JDK, фреймворки,
  статические импорты): не `import jakarta.validation.constraints.*;`, не `import static org.mockito.Mockito.*;`; в TS —
  не `import * as x`, если можно назвать нужное.
- **CODE.RULE.5** **Сгенерированный код руками не править** — перезапишется. Мешает (`*`-импорты и т.п.) — сказать мне:
  чинится шаблонами генератора или форматтером.
- **CODE.RULE.6** **Перед новым кодом — посмотреть, как похожее уже сделано в проекте** (2–3 места). Нормально —
  делать так же. Плохо (баг, устарело, против правил) или способы расходятся — не повторять и не «улучшать» молча:
  сказать мне, обсудим.

## CODE.LOG — журнал замечаний ревью (кратко, без имён и проектов)

После замечания ревьюера — строка сюда: что спросили → урок → правило. Проектная специфика (имя ревьюера, конкретные
классы) — в `<repo>/.claude/review.md`.

- **CODE.LOG.1** Фильтр/репозиторий для сущности из внутренней библиотеки сделали в приложении → «должно быть в
  библиотеке» (`CODE.RULE.1`).
- **CODE.LOG.2** Метод сервиса с типами приложения и без проверки входа, хотя рядом есть образец в соседней
  библиотеке → «посмотри, как сделано там» (`CODE.RULE.1`, «один в один»).
- **CODE.LOG.3** Явный `@Mapping` для поля, которое MapStruct маппит сам → «зачем перечислены поля» (`JAVA.RULE.1`).
- **CODE.LOG.4** `@Mapping` из-за того, что имя в API отличается от сущности одним регистром (`Timezone`/`TimeZone`) →
  «назови в OpenAPI так же — маппинг не нужен» (`JAVA.RULE.2`).
- **CODE.LOG.5** `System.nanoTime()` для замера длительности → «зачем наносекунды» — ответ: монотонность, а не точность
  (`CODE.RULE.3`).
- **CODE.LOG.6** «Сделай как у X» — взял за образец X, который сам отличается от остальных (пустое тело ошибки при
  общем формате у всех) → тестировщик вернул: «как у всех». Урок: образец-исключение — равняться на большинство, при
  сомнении спросить аналитика.
- **CODE.LOG.7** Общий метод для нескольких мапперов сделан отдельным бином через `uses` → «class → interface, default
  meetod» (`JAVA.RULE.3`). Третья ошибка с MapStruct (`CODE.LOG.3–4`) — перед правкой маппера смотреть соседние.
