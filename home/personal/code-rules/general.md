# Правила кода: общее

Проверить, когда код задачи написан, до отдачи на коммит (`/review-lessons`). Что сломалось — не сюда, а в `gotchas/`.

1. **Где живёт код.** Логика для сущности из внутренней библиотеки (общий `core`/`common`-модуль) — там же, где у
   соседних сущностей такая же логика. Посмотреть ближайший аналог: если у него фильтр/репозиторий/сервис в
   библиотеке — новый тоже туда, а не в приложение. Нет доступа к библиотеке — сказать об этом заранее, а не после ревью.
   **Делать как у аналога один в один:** та же сигнатура (типы параметров — из библиотеки/фреймворка, а не классы
   приложения, иначе в библиотеку не перенести), те же проверки входа, то же место. Перед сдачей — положить свой метод
   рядом с методом аналога и сравнить построчно.
2. **Каждая неочевидная строка — либо доказана, либо убрана.** Явная настройка, которая «кажется нужной» (явный маппинг
   поля, лишняя аннотация, защитная проверка), — проверить экспериментом: убрать → собрать → посмотреть результат. Не
   подтвердилось — не добавлять. Ответ ревьюеру «на всякий случай» не годится. Что осталось — в блок «Неочевидное в коде».
3. **Выбор API/подхода, по которому в проекте нет стандарта** (например, `nanoTime` vs `currentTimeMillis`) — иметь
   готовый ответ: где в проекте сделано так же + ссылка на первоисточник (документация, исходники).
4. **Импорты — только поимённые, без `*`**, в любом языке и из любого пакета (свой код, JDK, фреймворки, статические
   импорты): не `import jakarta.validation.constraints.*;`, не `import static org.mockito.Mockito.*;`; в TS — не
   `import * as x`, если можно назвать нужное.
5. **Сгенерированный код руками не править** — перезапишется. Мешает (`*`-импорты и т.п.) — сказать мне: чинится
   шаблонами генератора или форматтером.

## Журнал замечаний ревью (кратко, без имён и проектов)

После замечания ревьюера — строка сюда: что спросили → урок → пункт выше (или новый пункт/раздел). Проектная специфика
(имя ревьюера, конкретные классы) — в проект.

- Фильтр/репозиторий для сущности из внутренней библиотеки сделали в приложении → «должно быть в библиотеке» (п. 1).
- Метод сервиса с типами приложения и без проверки входа, хотя рядом есть образец в соседней библиотеке → «посмотри,
  как сделано там» (п. 1, «один в один»).
- Явный `@Mapping` для поля, которое MapStruct маппит сам → «зачем перечислены поля» (п. 2, «MapStruct»).
- `@Mapping` из-за того, что имя в API отличается от сущности одним регистром (`Timezone`/`TimeZone`) → «назови в OpenAPI
  так же — маппинг не нужен» (`java.md` → «MapStruct», «сначала выровнять»).
- `System.nanoTime()` для замера длительности → «зачем наносекунды» — ответ: монотонность, а не точность (п. 3).
