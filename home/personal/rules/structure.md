# Что куда писать

Дерево файлов с размерами и правило про размер — в `~/.claude/CLAUDE.md`. Здесь — куда что записывать.

## Записывать сразу

Всё, что я прошу запомнить, — **сразу в файл**, а не держать в голове до конца сессии. Нашёл сам (грабля, костыль,
находка по тикету, правило общения или работы, уточнение правила) — записать сразу, не спрашивая «Записать?», и в
ответе одной строкой сказать, что и куда. Спрашивать, только если непонятно, куда писать, или запись меняет смысл
принятого правила. После записи — обновить размер файла в дереве `CLAUDE.md`.

## Напоминать про коммит в `claude-config`

Изменил что-то в личных настройках (`~/.claude/CLAUDE.md`, `~/.claude/personal/**`, т.е. `/mnt/c/code/claude-config`)
— в конце ответа проверить `git -C /mnt/c/code/claude-config status --short` и неотправленные коммиты
(`git -C /mnt/c/code/claude-config log --oneline @{u}..`; «no upstream» — ветка ещё ни разу не отправлена, нужен
`git push -u origin main`) и, если что-то есть, отдельной строкой написать: какие файлы не закоммичены / сколько
коммитов не отправлено и команду. Коммитит и пушит пользователь сам, **из Windows** — команды для cmd/PowerShell, по
одной на строку, в блоке кода (`cd C:\CODE\claude-config`, `git add -A`, `git status --short`, `git commit -m "..."`,
`git push`).

## Где лежит физически

Личные настройки (`~/.claude/CLAUDE.md`, `~/.claude/personal/`) — в git-репозитории `/mnt/c/code/claude-config`
(`C:\CODE\claude-config`), в `~/.claude` — симлинки туда (`install.sh`); новый скилл — в
`claude-config/home/personal/skills/<имя>` + `./install.sh`. Всё проектное (`CLAUDE.md`, `.claude/**`,
`.sdkmanrc`/`.nvmrc`) — обычными файлами **в самом проекте**, в `claude-config` не переносить. Свои файлы в проекте
скрывать через `<repo>/.git/info/exclude`, а не `.gitignore` проекта (его не трогать). Новый проект — начать с
заготовки `templates/project/`.

## Что куда

| Что | Куда |
|---|---|
| Общение со мной: язык, переводы, краткость, объяснения, вопросы | `personal/rules/communication.md` |
| Как работаем над задачей: порядок, дисциплина изменений, проверка, сдача | `personal/rules/workflow.md` |
| Секреты, разрушительные шаги, разрешения | `personal/rules/safety.md` |
| Куда что писать (этот файл) | `personal/rules/structure.md` |
| **Правило написания кода** — как писать, чтобы ревьюер не спросил; что было написано «через одно место»; урок из замечания ревью | `personal/code-rules/<язык>.md` (общее — `general.md`; урок — строкой в «Журнал» `general.md`) |
| **Грабли по технологиям** (сломалось / не запускается): ОС и окружение, язык и фреймворки, БД, сборка и инструменты, внешние сервисы как продукты | `personal/gotchas/<тема>.md`, общими словами |
| Как поставить и выбрать Java/Node | `personal/environment.md` |
| Повторяющийся порядок действий, общий для всех проектов | `personal/skills/<имя>/SKILL.md` + симлинк `~/.claude/skills/<имя>` |
| Правило или устройство конкретного проекта (архитектура, команды, домен) | `<repo>/CLAUDE.md` |
| Параметры задач проекта: трекер, wiki, люди, эпики, калибровка оценок — общие для связанных репозиториев | `<repo>/.claude/tasks.md` (один на связанные репозитории; соседний подключает через `@../<repo>/.claude/tasks.md`) |
| Настройки списания часов проекта (задачи в двух Jira, часы в день) | `<repo>/.claude/timelog.md` — **без** `@`, читает только `/timelog` |
| **Грабли и костыли проекта**: как запускать тесты, почему сделано «через одно место», обходной путь | `<repo>/.claude/gotchas.md` |
| **Замечания ревью проекта** (MR/PR): кто, что просил, урок для проекта | `<repo>/.claude/review.md` (`@` из `CLAUDE.md`; общий урок — ещё и в журнал `code-rules/general.md`) |
| Повторяющийся порядок действий в проекте | `<repo>/.claude/skills/<имя>/SKILL.md` |
| Ход работы по тикету | `<repo>/.claude/tickets/<KEY>.md`, копия `personal/templates/ticket.md` |
| Ход работы по теме без тикета | `<repo>/.claude/tickets/<YYYY-MM-DD>-<тема>.md` |
| Личный контекст о пользователе и его планах | память ассистента |

**Новая тема — новый файл в своей папке**, а не дописывание в чужой: новая технология в граблях — `gotchas/<тема>.md`,
новый язык в правилах кода — `code-rules/<язык>.md`. Но не дробить: файл — под тему, а не под одну запись; мелочь —
в ближайший по смыслу. Новый файл — сразу `@`-импорт в `CLAUDE.md` и строка в дереве.

Как отличить:
- `CLAUDE.md` проекта / `gotchas.md`: «как устроено» → `CLAUDE.md`; «почему не работает очевидным способом и как
  обойти» → `gotchas.md`.
- `gotchas/` / `code-rules/`: сломалось, не компилируется, не запускается → `gotchas/` (формат: **симптом → причина
  (`файл:строка`) → как правильно**); работает, но ревьюер спросит «зачем так» → `code-rules/` (формат: **правило →
  почему → как проверить**).

**Какой `<repo>`.** Запись идёт в проект, **к которому относится** — где менялся код или где живёт грабля, а не где
открыта сессия. Касается связанных проектов обоих (бэк и его фронт: общий трекер, токены, сеть, git-сервер) — в тот,
куда подходит лучше, а в соседнем — пометка-ссылка «см. `../<другой>/…`».

**Документ по задаче** — в репозитории, **где меняется код задачи** (фронтовая задача → во фронте, даже если сессия
открыта в бэке). Код меняется в нескольких репозиториях — документ **в каждом**: суть и общие решения в обоих, «что
сделано» / «как проверить» / коммиты — про изменения именно этого репозитория; в «Пересечениях» — ссылка на соседний.
Мелкий вопрос в рамках текущего тикета — не новая тема: дописывать в документ тикета.

**Тема без тикета** (исследование, настройка окружения, договорённости о процессе) — такой же документ, ключ — дата и
тема (`2026-09-25-claude-settings.md`). Тема не про конкретный репозиторий (общие настройки ассистента) — документа не
нужно, итог — в самих файлах `personal/`.

**Грабля про технологию — в `personal/gotchas/`**, даже если нашлась в конкретном проекте: пригодится на том же стеке.
Формулировать через технологию, без путей, имён компании, классов и id проекта («Jackson 3 не видит `@JsonProperty` на
унаследованных полях», а не «`jsonMapper` в `BaseIntegrationTest`»). В проекте остаётся только его конкретика (класс,
команда, путь, версия) и ссылка «общее — `~/.claude/personal/gotchas/<тема>.md` → <раздел>». Грабля целиком про
устройство проекта (его конфиг, код, внешние библиотеки) — только в `<repo>/.claude/gotchas.md`. Грабля по ходу
тикета — сначала в документ тикета («Грабли»), про проект вообще — переносится в `gotchas.md`.

## Правила

- **Переносимость.** `personal/` я уношу с собой в другие проекты и компании. Там — только то, что верно везде, общими
  словами: ни адресов, ни ключей задач, ни имён людей и систем, ни кода, путей и id страниц проекта. **Всё
  специфичное для проекта — в `<repo>/`**, даже если выглядит как «общее правило работы». Проверка: будет ли это
  правдой в проекте на другом стеке, с другим трекером и командой? Нет или «не факт» — в проект. Нашлось и то и
  другое — разделить: общий принцип в `personal/` (с отсылкой «детали — в проекте»), конкретика — в `<repo>/`.
- **Не дублировать.** Одно правило — одно место. Другой файл может сослаться, но не копировать.
- **Всё грузится через `@`.** Правила, правила кода и грабли подключаются `@`-импортом из `CLAUDE.md` и есть в
  контексте всегда — ничего не надо «вспомнить открыть». Скиллом — только пошаговая процедура по запросу (оценка,
  ведение тикета): в контексте её `description`, тело — при вызове (и после `/compact` может потеряться — вызвать
  снова).
- **Всё моё в репозитории — скрыто от git.** Новое место в `<repo>/` — проверить (`git check-ignore -v <путь>`) и при
  необходимости добавить в `<repo>/.git/info/exclude`.
- Командные файлы, лежащие в git (общие заметки команды), — не наши: свои находки туда не дописывать.
