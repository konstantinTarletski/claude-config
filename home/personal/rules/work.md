# WORK — как работаем над задачей

Порядок по тикету (разбор → оценка → план → отчёт → коммит) — скилл `/ticket`. Здесь — то, что действует всегда.

- **WORK.TICK.1** Ссылка на тикет = разобрать, а не сделать → разбор по `/ticket` (шаг 1); код — только после
  «делай» (`USER.WORK.1`).
- **WORK.DISC.1** Нашёл попутно баг → сказать (файл, строка, суть) и спросить, делать ли отдельно; не править.
- **WORK.DISC.3** Сгенерированный код → после регенерации оставить только файлы, изменившиеся из-за моей правки.
- **WORK.DISC.4** Ветки и коммиты делаю я (`USER.PERM.3`) → ассистент даёт имя ветки и от чего её делать, ждёт
  «сделал». Формат ветки и коммита → `WORK.DISC.4` проекта.
- **WORK.DISC.5** Ветку проверить до первой правки кода → `git branch --show-current` в каждом репозитории задачи.
  Не та → **стоп, код не писать**, первой строкой: «⚠ Ветка не та: сейчас `<текущая>`, нужна `<ветка>` от `<база>` —
  создай и скажи "сделал"». Перед списком на коммит — проверить ещё раз.
- **WORK.DISC.6** Список на коммит (коммичу из IDE, `USER.WORK.4`) → команд `git add` / `commit` не давать; в конце
  ответа — блок на каждый репозиторий:
  ```text
  <репо>  <ветка>   1 added, 2 modified          ← так покажет IDE внизу окна Commit (нулевые не писать)
    отметить:                                     ← или «не отметить:» — какой список короче; нет чужих — не писать
      <файл>
  --------------- Commit message ------
  <сообщение>
  ------------- Перевод ---------------
  <перевод>
  ```
  После «закоммитил» → проверить самому (`git show --stat HEAD`, `git status -sb`): все ли файлы попали, запушено ли.
- **WORK.DISC.7** Причина во внутренней библиотеке (своя компания, соседняя команда, общий `core`/`common`) → стоп:
  сказать, где (класс, метод, строка) и что не так; в приложении не обходить, пока не скажу — обход прячет баг.
  Мне — заготовка комментария в трекер: цепочка вызовов, где сделано правильно, что и куда добавить.
- **WORK.RUN.1** Тяжёлый прогон (workflow, несколько субагентов) → только после «да»: сначала сказать, сколько агентов
  и что съест заметную часть лимита. «ultracode» / «не экономь токены» этого не отменяют.
- **WORK.RUN.2** Что-то идёт в фоне (агенты, долгая сборка) → каждый ответ начинать «⚠ в фоне работает <что>»
  (лимит мне не виден). Дорого или я недоволен → остановить сразу. Остановленное после новой сессии — не
  перезапускать без «да».
- **WORK.CHECK.1** Написал новый тест → проверить, что он реально запустился (тестов стало больше), а не просто
  «сборка зелёная»; число тестов — `tools/test-count.sh`.
- **WORK.CHECK.2** «Сборка» = полная, той же командой, что у меня и в CI (`gradle build`, `npm run build` + что CI гоняет
  ещё), а не её часть (`compileJava`, `tsc --noEmit`). На коммит — только после неё. Что гоняет CI → `WORK.CHECK.2`
  проекта.
- **WORK.REVW.1** Замечание из MR/PR или возврат из теста → сразу, до исправления, строкой в `<repo>/.claude/review.md`:
  дата, тикет, ревьюер → что просил (цитата + перевод) → урок для проекта. Общий урок → ещё и `CODE.LOG`
  (`/review-lessons add`).
