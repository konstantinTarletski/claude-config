# Ведение правил

Как **читать** правила — `RULES` в `~/.claude/CLAUDE.md` (всегда в контексте). Здесь — как их **вести**.

## Порядок правки

1. Правило (не грабля, не документ) → есть ли «меняй» (`RULES.EDIT.1`)? Нет → предложить текст и номер, ждать.
2. Куда → общее или проект (`RULES.PORT.1`, `FILES.WHERE`); файл; не дубль ли (`grep` по ключевым словам в
   `~/.claude/personal` и `<repo>/.claude`). Грабля → только ценная (`FILES.WHERE.5`).
3. Номер (`RULES.CODE.2`, `RULES.PROJ.4`); грабля — метка версии (`RULES.VER.2`).
4. Записать → Edit (`SAFE.PERM.1`); стиль — формулой «что → как» (`USER.PREF.8`); ссылки на номер из других мест —
   проверить.
5. Размер и дерево (`RULES.SIZE.1`); `claude-config` → что не закоммичено (`RULES.EDIT.2`).

## Правила ведения

- **RULES.CODE.2** Номер не переиспользуется → удалили правило — номер пропадает; новое — следующий свободный.
- **RULES.PROJ.4** Своё правило проекта в общем разделе → номер от 101 (`WORK.EST.101`).
- **RULES.PROJ.5** Что в проекте заведено до общего правила (имена токенов, раскладка, привычки команды) → не
  переделывать, записать в проекте с `(заменяет)`.
- **RULES.PROJ.8** Связанные репозитории (бэк + фронт одного клиента) → общее — в файлах главного (`.claude/work.md`,
  `integ.md`, `review.md`, общий `PROJ.TEAM`), остальные подключают `@../<главный>/.claude/…`. У каждого — свой
  `CLAUDE.md`, хотя бы тонкий (метка, `PROJ.ABOUT` в пару строк, `@`-ссылки), иначе сессия в нём общего не видит; в
  главном — список, кто подключает. `tech/` главного — только если та же технология и версия.
- **RULES.USER.3** Нет `~/.claude/user.md` → `./install.sh` в `claude-config`: свой профиль (`<логин>_*`) один — возьмёт;
  только чужой — скажет и не возьмёт; нет — подскажет шаблон; несколько — `./install.sh --profile <имя>`. Личное — в
  `~/.claude/private` (WSL: `--private /mnt/c/Users/<user>/.claude/private`); с 2.x — `--migrate`.
- **RULES.VER.2** Новая грабля → с меткой версии, на которой проверено (`[Spring 4.0]`, `[Spring Boot 2.x–3.1]`);
  верно и для другой — дописать; проверил, что там нет, — в «нет:». Только проверенное.
  В конце грабли — сколько раз пригодилась и когда последний раз: `(×3, 28.10.2026)`; новая — `(×1, <дата>)`. Без
  метки — с 3.0 не встречалась.
- **RULES.ONE.1** Одно правило — одно место → остальные ссылаются по номеру. Скиллы, шаблоны, проекты правил не
  повторяют (`RULES.ONE.2`).
- **RULES.ONE.3** Что задаётся настройкой Claude Code (разрешения, тема, модель, строка состояния) → только в
  `settings.json`; в правиле — только то, чего настройка не умеет.
- **RULES.PORT.1** `personal/` уносят в другие фирмы → только верное везде: без адресов, ключей задач, имён людей и
  систем, путей проекта. Проверка: правда ли это на другом стеке, с другой командой? Нет → в проект; и то и другое →
  принцип в `personal/`, конкретика в `<repo>/`. Личное — в `~/.claude/private`, не в репозитории.
- **RULES.SIZE.1** Изменил или добавил файл → строка и размер в дереве `docs/structure.md` (`wc -c` / 1024, до 0.1 КБ) и итог;
  новый код файла или утилита → строка в `~/.claude/CLAUDE.md` → «Коды файлов и утилиты». Утилита: в первых строках —
  что делает и как запускать; проектная — ещё команда в `PROJ.TOOLS`.
- **RULES.SIZE.2** Файл больше 12 КБ → ⚠ одной строкой: какой, сколько, как разбить; без «да» не разбивать.
- **RULES.SIZE.3** Итог больше 150 КБ → сказать, что разрослось.
- **RULES.NEW.1** Новая тема → новый файл со своим кодом (3–5 букв), но не под одну запись. Сразу: строка в `docs/structure.md`,
  код в «Коды файлов», `@`-импорт (импорты — через пустую строку, иначе превью зачёркивает `~~`).
- **RULES.NEW.2** Правила → только `@`-импортом (всегда в контексте); скилл → только процедура по вызову.
- **RULES.CLEAN.1** Грабля не воспроизводится, правило потеряло смысл, утилита не пригодилась → удалить (одной строкой —
  что и почему). Перестало только на новой версии → не удалять, пометить версиями, где верно.
  При выпуске версии → список граблей без метки `(×N, дата)` или с датой старше 6 месяцев = кандидаты на удаление;
  удалять — только после «да».
- **RULES.EDIT.2** Изменил `claude-config` → в конце ответа `git status --short` и неотправленные коммиты (`git log
  --oneline @{u}..`; нет upstream — `git push -u origin <ветка>`), сказать, что не закоммичено. Коммитит пользователь
  (`USER.PERM.3`) → команды для cmd по одной на строку; сообщения — на английском (`GIT.TRAP.3`).
- **RULES.EDIT.3** Где лежит → `~/.claude/CLAUDE.md`, `~/.claude/personal/` — симлинки в `claude-config` (`install.sh`);
  личное — `~/.claude/private`; новый скилл — `personal/skills/<имя>` + `./install.sh`; проектное — в проекте, скрыто
  через `.git/info/exclude`; новый проект — с `templates/project/`.
- **RULES.EDIT.4** Версии → теги (`v2.0`); крупная перестройка → отдельная ветка (не как тег: `release-3.0`) и PR, `main`
  не ломать. Что поменялось → `CHANGELOG.md`, простыми словами («объединили правила, выкинули дубли»); при выпуске
  «план» → «что сделано» с датой; первая строка — номер последней версии. Тег — на последний коммит версии.
  `README.md` → для людей: что даёт, быстрый старт, короткое дерево, ссылки; только текущее состояние, без «с версии
  X». У каждого короткого раздела, если есть полное описание, — сразу под ним строка «Подробнее — <ссылка>». Техническое → `docs/` по темам (`structure.md` — дерево с размерами, `install.md`, `how-it-works.md` …);
  история → `CHANGELOG.md`, переход → `v*-to-v*.md`.
- **RULES.MIGR.2** Переезд проекта → по инструкциям рядом, по очереди: `v1-to-v2.md`, `v2.0-to-v2.1.md`,
  `v2.1-to-v2.2.md`, `v2.2-to-v3.0.md`; в конце — метка версии.
