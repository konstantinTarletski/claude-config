# Общие правила для всех проектов

Оглавление, правила ведения правил и подключение. Все файлы правил подключены `@`-импортами внизу и **грузятся
всегда** — ничего не надо «вспомнить открыть». Куда писать находки по ходу работы — `FILES`.

## RULES — ведение правил

### RULES.CODE — номера

- **RULES.CODE.1** Номер правила — **`ФАЙЛ.РАЗДЕЛ.N`** (`COMM.LANG.3`): коды файла и раздела — 3–5 латинских букв,
  `N` — число; номер всегда из трёх частей. Код файла — в дереве ниже.
- **RULES.CODE.2** **Номер не переиспользуется**: удалили правило — номер пропадает, новое правило — следующий свободный
  номер в разделе. Ссылки «см. `WORK.DISC.5`» не ломаются.
- **RULES.CODE.3** В `tech/` разделы одинаковые во всех файлах: **`SETUP`** — установка, **`RULE`** — как писать
  (правило → почему → как проверить), **`TRAP`** — грабли (симптом → причина → как правильно). Чего нет — раздела нет.
- **RULES.CODE.4** Найти правило по номеру — общее и проектное сразу:
  `grep -rn "WORK.DISC.5" ~/.claude/CLAUDE.md ~/.claude/personal <repo>/CLAUDE.md <repo>/.claude`.

### RULES.PROJ — правила проекта

- **RULES.PROJ.1** Приоритет: **моё слово в чате → правило проекта → общее правило.**
- **RULES.PROJ.2** У проекта **та же раскладка и те же номера**: `<repo>/.claude/work.md` ↔ `rules/work.md`,
  `<repo>/.claude/tech/java.md` ↔ `tech/java.md`. В проекте — только отличия и конкретика (адреса, команды, классы).
- **RULES.PROJ.3** Правило проекта с тем же номером **дополняет** общее; **заменяет** — только с пометкой
  **`(заменяет)`** после номера.
- **RULES.PROJ.4** Своё правило проекта в общем разделе — номер **от 101** (`WORK.EST.101`), чтобы не столкнуться с
  новыми общими номерами.
- **RULES.PROJ.5** Что в проекте заведено **до** общего правила (имена токенов, раскладка, привычки команды) — не
  переделывать, а записать в проекте исключением `(заменяет)`.
- **RULES.PROJ.6** Разделы, которые есть только у проекта, — код **`PROJ`** в `<repo>/CLAUDE.md`: `PROJ.ABOUT` о проекте
  и соседних репозиториях, `PROJ.CMD` команды, `PROJ.ARCH` архитектура, `PROJ.TEAM` люди и роли, `PROJ.TOOLS` утилиты
  проекта.
- **RULES.PROJ.8** **Связанные репозитории** (бэк + фронт с общим трекером, людьми, калибровкой): общее — в файлах
  главного репозитория (`.claude/work.md`, `.claude/integ.md`, `.claude/review.md`; общий `PROJ.TEAM` — тоже там),
  второй подключает их `@../<главный>/.claude/…`; правила, которые второго не касаются, — с пометкой «(только
  <репо>)»; свои правила второго — в его файлах, номера — после номеров главного.
- **RULES.PROJ.7** **Метка версии** — первая строка `<repo>/CLAUDE.md`: `<!-- claude-config: 2.0 -->`. Командный
  `CLAUDE.md`, лежащий в git проекта, — не наш (`FILES.WHERE.7`): своё — в `.claude/`.

### RULES.VER — версии технологий

- **RULES.VER.1** Правило/граблю с меткой версии (`[Spring Boot 3+]`, `[Angular ≤ 15]`, `[Jackson 3]`) применять,
  только если версия в проекте подходит; версию проекта смотреть до первой правки (`build.gradle`, `package.json` —
  `SETUP`). Без метки — для всех версий.
- **RULES.VER.2** Новая грабля — с меткой версии, на которой проверено, даже если не уверен, что другие версии ведут себя
  иначе. Метка — одна версия, диапазон или список: `[Spring 4.0]`, `[Spring Boot 2.x–3.1]`, `[Angular 15, 17]`;
  выяснилось, что верно и для другой версии, — дописать её в метку. Правил под одну версию стало много — отдельный файл (`tech/spring-boot-2.md`).

### RULES.ONE — одно правило — одно место

- **RULES.ONE.1** Одно правило — **одно место**; другие файлы ссылаются по номеру («перевод — по `COMM.LANG.3`»), а не
  копируют текст.
- **RULES.ONE.2** Скиллы, шаблоны и документы проекта правил не повторяют — только ссылка.

### RULES.PORT — переносимость

- **RULES.PORT.1** `personal/` уносится в другие проекты и компании и им пользуются другие люди: там **только то, что
  верно везде**, общими словами — ни адресов, ни ключей задач, ни имён людей и систем, ни кода, путей и id страниц
  проекта. Проверка: будет ли это правдой на другом стеке, с другим трекером и командой? Нет или «не факт» — в проект.
  Нашлось и то и другое — общий принцип в `personal/` (с отсылкой «детали — в проекте»), конкретика — в `<repo>/`.

### RULES.SIZE — размер

- **RULES.SIZE.1** Изменил, добавил или удалил файл — **обновить его строку и размер в дереве** (`wc -c` / 1024, до
  0.1 КБ) и итог.
- **RULES.SIZE.2** Файл больше 12 КБ — **⚠ и сказать** одной строкой: какой, сколько, как разбить (по темам — новый файл
  в той же папке). Без моего «да» не разбивать.
- **RULES.SIZE.3** Итог больше 150 КБ — сказать: что разрослось и что можно сжать или вынести.

### RULES.NEW — новый файл

- **RULES.NEW.1** Новая тема — **новый файл со своим кодом** (3–5 букв) в своей папке, а не дописывание в чужой: новая
  технология — `tech/<тех>.md`. Но не дробить: файл — под тему, а не под одну запись; мелочь — в ближайший по смыслу.
  Сразу — строка в дереве и `@`-импорт.
- **RULES.NEW.2** **Правила — только `@`-импортом** (всегда в контексте, ничего не надо «вспомнить открыть»). Скилл —
  только пошаговая процедура по запросу: в контексте его `description`, тело — при вызове (после `/compact` может
  потеряться — вызвать снова).

### RULES.CLEAN — устаревшее удалять

- **RULES.CLEAN.1** Грабля больше не воспроизводится (починили в библиотеке, поменялось окружение), правило потеряло
  смысл, утилита не подходит или не пригодилась — **удалить** (номер пропадает — `RULES.CODE.2`), одной строкой сказать,
  что и почему. Перестало только на новой версии, а старая где-то ещё живёт — **не удалять, а пометить версией или
  версиями**, для которых грабля/костыль верны (`[Spring 4.0–4.3]`, `RULES.VER.2`). Старое остаётся в git-истории `claude-config`.

### RULES.EDIT — как меняем правила

- **RULES.EDIT.1** **Правила** (`CLAUDE.md`, `personal/rules/`, `RULE` и `SETUP` в `personal/tech/`, правила проекта)
  меняю **только после «меняй»**: сначала обсуждаем, я предлагаю текст и номер. **Сразу, без «меняй»** — документы
  задач, грабли (`TRAP`, общие и проектные), замечания ревью, калибровка оценок, память (`FILES.NOW.1`).
- **RULES.EDIT.2** Изменил что-то в `claude-config` — в конце ответа проверить `git -C /mnt/c/code/claude-config status
  --short` и неотправленные коммиты (`git log --oneline @{u}..`; «no upstream» — ветка ещё ни разу не отправлена, нужен
  `git push -u origin <ветка>`) и сказать, что не закоммичено. Коммитит и пушит
  пользователь сам, **из Windows** — команды для cmd по одной на строку (`cd C:\CODE\claude-config`, `git add …`,
  `git status --short`, `git commit -m "…"`, `git push`); сообщения коммитов — **на английском**.
- **RULES.EDIT.3** Где лежит физически: `~/.claude/CLAUDE.md` и `~/.claude/personal/` — симлинки в репозиторий
  `claude-config` (`install.sh`); новый скилл — `personal/skills/<имя>` + `./install.sh`. Всё проектное — обычными
  файлами в самом проекте, скрыто через `<repo>/.git/info/exclude`. Новый проект — с заготовки `templates/project/`.
- **RULES.EDIT.4** Версии `claude-config` — тегами (`v2.0`), крупная перестройка — в отдельной ветке и через PR, `main`
  не ломать (им пользуются другие); что поменялось — `CHANGELOG.md`.

### RULES.MIGR — переезд проекта на новую версию

- **RULES.MIGR.1** Проект без метки `<!-- claude-config: … -->` или со старой версией — сказать одной строкой «проект на
  v1, перевести на v2 по `migrate/v1-to-v2.md`?» и ждать «да».
- **RULES.MIGR.2** Переезд — строго по `personal/migrate/v1-to-v2.md` (читать при переезде, не грузится всегда); в конце
  — метка версии.
