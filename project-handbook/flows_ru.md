# Flows

Порядок работы с проектом. Термины — `terms.md`; цель для бэкенд-тестов — `backend-test-rules.md`.

## Когда запускаем flow

- Его результата в проекте ещё нет.
- Результат устарел — с коммитов в его шапке (`git diff --name-status <коммит>` в каждом репозитории):
  - изменились файлы из его таблицы → обновить только эти строки;
  - появилась новая точка входа (REST-контроллер, планировщик, обмен с другой системой) → проверить, не новая ли это
    ключевая часть.

  Ничего из этого → результат актуален, сколько бы коммитов ни прошло.
- Попросили.

## 1. Ключевые части системы

Находим части системы, их важность и основные пути. Flow — про всю систему: бэкенд и фронт в одной таблице.

Результат — файл:

```text
# Ключевые части системы

Дата: <ГГГГ-ММ-ДД>
Коммиты: <репозиторий> <коммит>, <репозиторий> <коммит>
Подтвердили: <кто, когда> | ещё нет

## Части

| # | Часть | Что делает | Важность | Экран (фронт) | Вход (бэк) | Где логика | SQL |
|---|---|---|---|---|---|---|---|
| 1 | <часть> | <одна строка> | critical | <приложение>: <адрес экрана><br>`<Экран>` | `POST /<путь>`<br>`<Контроллер>.<метод>` | `<Сервис>.<метод>` | `<Маппер>.<метод>` |

## Основные пути

1. <путь>: <шаг> → <номер части> → <номер части>
```

- **Коммиты** — каждого репозитория, на файлы которого есть ссылки (бэкенд, фронт).
- Строки — сначала critical, потом major, потом minor; ключевые — critical и major.
- **#** — номер части; в основных путях ссылаемся на него.
- **Важность** — critical, major, minor (`terms.md`).
- **Экран (фронт)** — приложение (если их несколько), адрес экрана и файл экрана; экрана нет (машинный API,
  планировщик) — «—».
- **Вход (бэк)** — REST-запрос, планировщик или операция обмена с другой системой и `Класс.метод`, который его
  принимает.
- **Где логика** — `Класс.метод` с бизнес-логикой.
- **SQL** — `Маппер.метод`, если в запросе есть бизнес-логика; нет — «—».
- Ссылка — на файл, метод — текстом; номера строк не ставим: устаревают после первой правки.

Список подтверждает команда (аналитик, тимлид); в шапке — кто и когда.

## 2. Бэкенд-тесты: анализ и план миграции

Нужен результат «1. Ключевые части системы»: без него не посчитать их покрытие. Цель, к которой ведёт план, —
`backend-test-rules.md`.

### 2.1 Анализ

1. **Покрытие:** общее, бизнес-логики, ключевых частей. Чем мерить — инструмент стека (Java — JaCoCo). SQL инструмент
   покрытия не видит → подсчётом: сколько запросов с бизнес-логикой и сколько из них с тестом SQL.
2. **Двойное тестирование:** тесты, которые проверяют одно и то же, в том числе на разных уровнях (юнит-тест, тест
   SQL, интеграционный).
3. **Тесты, которые ничего не проверяют:**
   1. не запускаются: выключены (`@Disabled`, `skip`), закомментированы или метод без аннотации теста;
   2. в тесте нет проверок (`assert`) или проверка ничего не проверяет;
   3. упавший тест не роняет сборку или CI.
4. **Структура тестов:**
   1. неправильное наследование;
   2. дублирование тестового кода — что можно вынести в хелперы и базовые классы.
5. **Имена и папки:**
   1. где имена хорошие;
   2. где похожие тесты называются по-разному;
   3. где похожие SQL-скрипты называются по-разному;
   4. где похожие файлы JSON, CSV и т. п. называются по-разному;
   5. нет ли SQL, CSV, JSON и т. п. прямо в коде тестов;
   6. лежат ли тесты в «своих» папках и пакетах.
6. **Ключевые части и основные пути** (таблица из «1. Ключевые части системы»):
   1. насколько протестированы ключевые части — по ссылкам таблицы: вход → интеграционный тест, где логика → юнит-тест
      и покрытие, SQL → тест SQL;
   2. насколько протестированы основные пути;
   3. что надо покрыть, чтобы закрыть самые важные пути в системе.
7. **Формулы и хелперы:**
   1. если есть формулы или расчёты — есть ли для них отдельные хорошие тесты;
   2. если есть хелперы (классы, методы), которые делают сложные или критичные вещи, — есть ли хорошие тесты и для них.
8. **Тестовые данные:**
   1. у каждого тестового класса свои данные или общие на всех; зависят ли тесты от порядка запуска;
   2. меняют ли тесты общие данные;
   3. похожи ли личные данные на настоящие (личные коды, имена, e-mail);
   4. зависят ли тесты от системной даты и времени.
9. **Интеграционные тесты — зависимости и моки:**
   1. запускается настоящее приложение или тестовая копия его конфигурации;
   2. на какой базе запускаются — в Docker? Если нет — насколько сложно на него перейти;
   3. зависят ли от других систем (например, etcd, X-Road); если да — насколько сложно от них отключиться;
   4. проверяются ли security и права (permissions) на эндпоинты;
   5. что замокано — внешние системы или свои сервисы; насколько сложно «выкинуть» мок.
10. **Интеграционные тесты — какие пути покрыты:** насколько они важны и насколько хорошо описаны.
11. **Планировщики:** как тестируются и что с ними происходит при запуске интеграционных тестов.

### 2.2 Отчёт и план

Делаем три раза: когда проект только получили, в процессе переделки и после завершения изменений. В имени файла
отчёта — дата.

1. **Когда проект только получили:** по каждому пункту цели — сколько нарушений, где, насколько сложно исправить и
   когда проверяли. Пустых клеток нет: значение или «—».

   | Пункт цели | Нарушений | Где | Сложность | Проверено |
   |---|---|---|---|---|
   | `backend-test-rules.md → 1. Все тесты → 1.5` | 0 | — | — | 2026-11-20 |
   | `backend-test-rules.md → 1. Все тесты → 1.6` | 3 | `A`, `B`, `C` | низкая | 2026-11-20 |
   | `backend-test-rules.md → 2. Юнит-тесты → 2.1` | — | — | — | не проверяли |

   - **Нарушений** — число; `0` с датой — проверили, нарушений нет.
   - **Где** — ссылки на тесты (классы, файлы).
   - **Проверено** — дата проверки; не смотрели — «не проверяли».
2. **План достижения цели** (когда проект только получили и в процессе) — таблица по шагам, подшаги — строками `1.1`,
   `1.2`; у подшага цель и числа не пишем — они у шага. Пункт цели — полным адресом заголовков, не голым номером:

   | Готово | # | Что делаем | Цель | Тестов затронет | Файлов всего |
   |---|---|---|---|---|---|
   | [x] | 1 | Интеграционные тесты — на настоящее приложение | `backend-test-rules.md → 3. Интеграционные тесты → 3.3` | 120 | 35 |
   | [x] | 1.1 | Один класс — на настоящем приложении | | | |
   | [ ] | 1.2 | Остальные классы — туда же | | | |
   | [ ] | 1.3 | Тестовую копию конфигурации — удалить | | | |
   | [ ] | 2 | Убрать двойные тесты | `backend-test-rules.md → 1. Все тесты → 1.1` | 14 | 9 |

   `[x]` — тесты шага закоммичены и полная сборка зелёная; шаг с подшагами — когда готовы все его подшаги.

3. **Когда закончили:** что сделано по каждому пункту цели; если не сделано — почему именно.
4. **Тестовые классы по пунктам цели** — количество и таблица: интеграционные — по классам, юнит — по пакетам.

   | Интеграционный тест (с пакетом) | Что покрывает | Состояние |
   |---|---|---|
   | `<пакет>.A1ITest` | ключевую логику 1 | OK, ничего делать не надо |

   | Пакет юнит-тестов | Что тестирует (коротко) | Покрытие пакета | Что нужно доделать |
   |---|---|---|---|

5. **Покрытие до начала переделки и после** — одни и те же пункты:
   1. юнит-тестов в целом;
   2. юнит-тестов ключевых частей;
   3. интеграционных в целом;
   4. интеграционных ключевых частей (если отличается);
   5. всех тестов вместе.

### 2.3 Перед переделкой тестов

Можно ли менять код, если тест нашёл баг, — спросить и записать до начала работы над тестами. Нельзя → тест фиксирует
текущее поведение, баг — в список проблем проекта со ссылкой на тест.
