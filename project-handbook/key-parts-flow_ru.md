# Ключевые части системы — как найти

Термины — `terms_ru.md`.

## Когда запускаем flow

- Его результата в проекте ещё нет.
- Результат устарел — с коммитов в его шапке (`git diff --name-status <коммит>` в каждом репозитории):
  - изменились файлы из его таблицы → обновить только эти строки;
  - появилась новая точка входа (REST-контроллер, планировщик, обмен с другой системой) → проверить, не новая ли это
    ключевая часть.

  Ничего из этого → результат актуален, сколько бы коммитов ни прошло.
- Попросили.

## Как составить список

Находим части системы, их важность и основные пути. Flow — про всю систему: бэкенд и фронт в одной таблице.

Результат — файл:

```text
# Ключевые части системы

Дата: <ГГГГ-ММ-ДД>
Коммиты: <репозиторий> <коммит>, <репозиторий> <коммит>
Подтвердили: <кто, когда> | ещё нет

## Части

| # | Часть | Что делает | Важность | Экран (фронт) | Вход (бэк) | Где логика | SQL |
|---|---|---|---|---|---|---|---|
| 1 | <часть> | <одна строка> | critical | <приложение>: <адрес экрана><br>`<Экран>` | `POST /<путь>`<br>`<Контроллер>.<метод>` | `<Сервис>.<метод>` | `<Маппер>.<метод>` |

## Основные пути

1. <путь>: <шаг> → <номер части> → <номер части>
```

- **Коммиты** — каждого репозитория, на файлы которого есть ссылки (бэкенд, фронт).
- Строки — сначала critical, потом major, потом minor; ключевые — critical и major.
- **#** — номер части; в основных путях ссылаемся на него.
- **Важность** — critical, major, minor (`terms_ru.md`).
- **Экран (фронт)** — приложение (если их несколько), адрес экрана и файл экрана; экрана нет (машинный API,
  планировщик) — «—».
- **Вход (бэк)** — REST-запрос, планировщик или операция обмена с другой системой и `Класс.метод`, который его
  принимает.
- **Где логика** — `Класс.метод` с бизнес-логикой.
- **SQL** — `Маппер.метод`, если в запросе есть бизнес-логика; нет — «—».
- Ссылка — на файл, метод — текстом; номера строк не ставим: устаревают после первой правки.

Список подтверждает команда (аналитик, тимлид); в шапке — кто и когда.
