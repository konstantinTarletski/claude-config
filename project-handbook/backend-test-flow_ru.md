# Бэкенд-тесты — как прийти к цели

Цель — `backend-test-rules_ru.md` («Бэкенд-тесты — как должно быть»), термины — `terms_ru.md`. Пункты цели пишем
адресом заголовков, не голым номером: в плане и отчёте — с файлом (`backend-test-rules_ru.md → 2. Общее → 2.5`),
ниже в тексте — без него (`2. Общее → 2.5`).

## 1. До начала

- **Можно ли менять код, если тест нашёл баг.** По умолчанию — **нельзя совсем**: тест фиксирует текущее поведение,
  баг — в `project-issues.md` части со ссылкой на тест. Разрешили менять → записать: кто, когда, что можно.
- **Ключевые части системы** — готов список (`key-parts-flow_ru.md`): без него не посчитать покрытие ключевых частей и
  не понять, что делать первым.

## 2. Анализ

1. Проверяем все тесты по каждому пункту `backend-test-rules_ru.md`.
2. Замеряем покрытие — инструментом стека (Java — JaCoCo). С этим числом сравниваем после каждого шага:
   1. юнит-тестов в целом;
   2. юнит-тестов бизнес-логики;
   3. юнит-тестов ключевых частей;
   4. интеграционных в целом;
   5. интеграционных ключевых частей (если отличается);
   6. всех тестов вместе.
3. **После первого анализа — достижим ли каждый пункт цели** и сколько часов на него с AI. Не достижим или очень
   много работы → почему и рекомендация: до скольки снизить норму или что сделать, чтобы дойти. Обсуждаем
   с пользователем; снизить — только с его разрешения и по каждому пункту отдельно (так `2. Общее → 2.10` работает
   для покрытия). Результат — в первый отчёт по нарушениям («3.1»), сниженные нормы — в общий отчёт («3.2», «Цель» и
   «Причина»).

## 3. Отчёты

Два отчёта: по нарушениям — пока они есть, общий — всегда. Отчёты и планы («4.3») — в `docs/tests/` части.

### 3.1 Отчёт по нарушениям — `backend-violations-<ГГГГ-ММ-ДД>.md`

Делаем на шаге 0 (первый — результат «2. Анализ», пункты 1 и 3), пока не закончен шаг 1 и потом — когда снова
появились нарушения. Кроме шага 0: остались только покрытие и недостающие тесты (группы 1, 5, 6, 7 — их закрывают
шаги 3–5 по плану) → не делаем, покрытие видно в общем отчёте («3.2»). Нет отчёта по нарушениям → нарушений в группах
2, 3, 4 нет. Храним не больше 10: появился одиннадцатый → самый старый удаляем.

Заголовок — «Отчёт по нарушениям тестов <ГГГГ-ММ-ДД>», в шапке — к какому шагу он относится: `Шаг 0 — первый отчёт`,
`Шаг 1`; посреди шага — `В процессе: шаг 1`. Таблица — по каждому пункту цели; пустых клеток нет: значение или «—».
Нужно что-то пояснить → текстом после таблицы, коротко — до неё.

| Пункт цели | Нарушений | Где | Достижим | Время с AI, ч | Почему, рекомендация | Проверено |
|---|---|---|---|---|---|---|
| `backend-test-rules_ru.md → 2. Общее → 2.5` | 0 | — | — | 0 | — | 2026-11-20 |
| `backend-test-rules_ru.md → 3. Архитектура и структура → Код тестов → 3.1` | 3 | `A`, `B`, `C` | да | 1 | — | 2026-11-20 |
| `backend-test-rules_ru.md → 1. Покрытие → 1.1` | 50% при норме 60%, не хватает 1700 строк | `X`, `Y` — больше всего непокрытого | да, без скопированных библиотек | 0 | 3000 строк — чужие библиотеки; считать без них | 2026-11-20 |
| `backend-test-rules_ru.md → 1. Покрытие → 1.2` | — | — | — | — | — | не проверяли |

- **Нарушений** — число; `0` с датой — проверили, нарушений нет; у покрытия — сколько сейчас при какой норме и сколько
  не хватает.
- **Где** — ссылки на тесты (классы, файлы); у покрытия — классы, где больше всего непокрытого.
- **Достижим** — можно ли дойти до цели; нет → почему и рекомендация («2. Анализ» → 3).
- **Время с AI, ч** — сколько часов, чтобы убрать все нарушения пункта, если тесты пишет AI, а человек проверяет.
- **Проверено** — дата проверки; не смотрели — «не проверяли».

### 3.2 Общий отчёт — `backend-report.md`

Один файл, обновляем после каждого шага и каждой работы по тестам («4.3»). Перед таблицей — дата обновления
жирным, как заголовок.

**2026-11-27**

| Покрытие | В начале | Сейчас | Цель | Причина |
|---|---|---|---|---|
| юнит-тестов в целом | 41% | 55% | 60% | — |
| юнит-тестов бизнес-логики | 48% | 66% | 70% | снижено с 80%: <почему>; разрешил <кто>, <дата> |
| юнит-тестов ключевых частей | 52% | 78% | 80% | — |
| интеграционных в целом | 30% | 44% | — | нормы нет |
| интеграционных ключевых частей | 35% | 61% | — | нормы нет |
| всех тестов вместе | 58% | 70% | — | нормы нет |

- **Покрытие** — те же пункты, что в анализе («2. Анализ» → 2).
- **В начале** — замер на шаге 0 («2. Анализ» → 2).
- **Цель** — норма из `1. Покрытие`; снижена («2. Анализ» → 3) → новая, а в «Причина» — почему, кто и когда разрешил.

После таблицы — ссылка на последний отчёт по нарушениям, нет его — «Нарушений нет». Всё, что нужно записать, —
текстом там же: например, покрытие упало с прошлого раза → почему.

## 4. План и работа

### 4.1 Шаги

**Шаг 0. Первый отчёт** — до любых правок: анализ («2. Анализ»), первый отчёт по нарушениям («3.1») и общий отчёт
(«3.2»). Это точка отсчёта: колонка «В начале» общего отчёта.

**Шаг 1. Имеющиеся тесты — в порядок.** Новых тестов не пишем.

1. **Сломанные, выключенные и нестабильные** — чиним всегда и сразу; падают время от времени — переделываем. Падение
   сборки при упавшем тесте можно включить сразу, для себя, — чтобы видеть все упавшие.
   `2. Общее → 2.4–2.8`.
2. **Правильность написанных:** двойные тесты — пометить для удаления; тест не своего уровня — перенести на свой
   уровень (это не новый тест; недостающие — в шагах 3–5); тест, который проверяет не то, — пометить для удаления;
   тест, который ничего не проверяет, — починить.
   `2. Общее → 2.1, 2.2, 2.3`.
3. **Структура:** имена и пакеты → помощники и базовые классы → файлы (CSV, JSON, копии) → тестовые данные.
   `3. Архитектура и структура → Код тестов`, по порядку пунктов.
4. **Всё остальное, что не требует новых тестов:** личные данные — выдуманные; интеграционные — на настоящем
   приложении, через настоящие фильтры безопасности, с моками внешних систем (свои сервисы — только как исключение),
   на Testcontainers; планировщики в них выключены. Тесты сгенерированного кода — пометить для удаления.
   `2. Общее → 2.9`, `3. Архитектура и структура → Интеграционные тесты`, `4. Фильтры → 4.2`.

**Шаг 2. Находки проверки кода** — есть отчёты GLASS WORKS или другой проверки → тест на каждую находку. Код менять
нельзя («1. До начала») → тест фиксирует, как есть сейчас, находка — в `project-issues.md` части.

**Шаги 3–5. Юнит-тесты, интеграционные, остальные** — старые тесты приводим к правилам, недостающие дописываем до
нормы покрытия (с учётом сниженных, «2. Анализ» → 3). Внутри шага — по ключевым частям, critical первыми: кончится
время — важное уже сделано. Шаг 5 — всё, что не попало в шаги 3 и 4: SQL-тесты (мапперы, репозитории),
планировщики и тому подобное.
Пункты цели: шаг 3 — `1. Покрытие`, `5. Юнит-тесты`; шаг 4 — `6. Интеграционные тесты`; шаг 5 —
`7. Другие тесты`, для планировщиков — и `1. Покрытие → 1.3`.

### 4.2 Правила для всех шагов

- **Перед любой работой по тестам — план («4.3»)**, дальше идём по нему.
- **Не трогаем то, что уже по правилам:** тест проходит, со временем падать не начнёт, случайно не падает и написан
  по всем правилам цели (`4. Фильтры → 4.1`).
- **Новые тесты — только по всем правилам цели и на структуре шага 1**, чтобы потом не переделывать.
- **Любой тест удаляем, только когда** его заменили нашим правильным или он стал не нужен — и покрытие после
  удаления не ниже нормы — из `backend-test-rules_ru.md` или сниженной («2. Анализ» → 3); ниже нормы →
  `2. Общее → 2.10`. До этого — помечаем в `project-issues.md` части, со ссылкой на строку отчёта или таблицы
  плана, где сказано почему; не `@Disabled` (иначе нарушим `2. Общее → 2.5`). Удаляем перед сборкой и
  коммитом. Сломанные и выключенные не помечаем, а чиним сразу (шаг 1).

  | Тест | Почему (ссылка) | Чем заменён | Удалён |
  |---|---|---|---|
  | `<пакет>.ATest.method` | `tests/backend-violations-<ГГГГ-ММ-ДД>.md` → `4. Фильтры → 4.2`: проверяет сгенерированный код | — | [ ] |

- **Конец шага:** полная сборка с покрытием → общий отчёт («3.2»): новые числа, упало → почему, текстом после
  таблицы → шаг 1 не закончен или появились нарушения → отчёт по нарушениям («3.1») → коммит.
- **Много изменений → предложить промежуточный коммит**, не дожидаясь конца шага.
- **В коммите все тесты зелёные.** Ни одного упавшего теста в коммите.

### 4.3 План — `backend-plan-<шаг или тема>-<ГГГГ-ММ-ДД>.md`

Свой файл на каждый шаг 1–5 и на любую другую работу по тестам; дата — когда составили. Примеры имён:
`backend-plan-step1-2026-11-27.md`, `backend-plan-excel-statistics-2026-11-27.md`. Заголовок —
«План <шаг N «название» или тема> <ГГГГ-ММ-ДД>». Составляем до начала работы, ведём в процессе: сделали строку →
`[x]`. Работа закончена → закрываем план: в самом верху, под заголовком, — «Закончено <ГГГГ-ММ-ДД>»; что не сделали
или от чего отступили — в `project-issues.md` части, со ссылкой на строку плана; общий отчёт («3.2») обновляем.
Пришлось переделать — правим тот же файл.
Незакрытый план — только один. Начали новую работу, а старый план не закрыт → старый переименовываем
в `…-invalid.md`, а в самом верху, под заголовком, пишем: «Заменён на `<новый план>`»; знаем почему — и почему.

Строки — что делаем, подстроки — `1.1`, `1.2`; у подстроки цель и числа не пишем — они у строки.

План шага 1 «Имеющиеся тесты — в порядок»:

| Готово | # | Что делаем | Цель | Время с AI, ч | Тестов затронет | Файлов всего | Комментарий, допущение |
|---|---|---|---|---|---|---|---|
| [ ] | 1 | Сломанные, выключенные и нестабильные — починить | `backend-test-rules_ru.md → 2. Общее → 2.4–2.8` | 4 | 10 | 2 | |
| [x] | 1.1 | `ATest` — на подменяемых часах | | | | | |
| [ ] | 1.2 | `BITest` — не зависит от порядка запуска | | | | | |
| [ ] | 2 | Двойные тесты — пометить для удаления | `backend-test-rules_ru.md → 2. Общее → 2.1` | 2 | 14 | 9 | 2 теста остаются: старый формат файла ещё принимается, разрешено (решение от <дата>) |

- `[x]` — закоммичено и полная сборка зелёная; строка с подстроками — когда готовы все её подстроки. Работа готова
  целиком — когда готовы все строки и покрытие проверено («4.2 Правила для всех шагов» → «Конец шага»).
- **Время с AI, ч** — до начала работы: объём виден заранее, а не на середине.
- **Комментарий, допущение** — где работа отступает от цели: от какого пункта, сколько тестов, почему; разрешено ли —
  «разрешено (решение от <дата>)»; что ещё нужно согласовать. Сказать нечего — пусто.
