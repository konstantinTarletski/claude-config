# Бэкенд-тесты — как прийти к цели

Цель — `backend-test-rules_ru.md` («Бэкенд-тесты — как должно быть»), термины — `terms_ru.md`. Пункты цели пишем
адресом заголовков, не голым номером: в плане и отчёте — с файлом (`backend-test-rules_ru.md → 1. Все тесты → 1.5`),
ниже в тексте — без него (`1. Все тесты → 1.5`).

| Этап | Что | Результат |
|---|---|---|
| 1 | До начала | решение про код, список ключевых частей |
| 2 | Анализ | нарушения по пунктам цели, покрытие; после первого — сложность и какие нормы снизить |
| 3 | Отчёт | нарушения, покрытие, сниженные нормы, с датой — в начале и после каждого шага |
| 4 | План и работа | шаги 1–5, после каждого — сборка, покрытие, отчёт, коммит |
| 5 | Когда закончили | стандартный отчёт (этап 3) |

## 1. До начала

- **Можно ли менять код, если тест нашёл баг.** По умолчанию — **нельзя совсем**: тест фиксирует текущее поведение,
  баг — в список проблем проекта со ссылкой на тест. Разрешили менять → записать: кто, когда, что можно.
- **Ключевые части системы** — готов список (`key-parts-flow_ru.md`): без него не посчитать покрытие ключевых частей и
  не понять, что делать первым.

## 2. Анализ

1. Проверяем все тесты по каждому пункту `backend-test-rules_ru.md`.
2. Замеряем покрытие — инструментом стека (Java — JaCoCo). С этим числом сравниваем после каждого шага:
   1. юнит-тестов в целом;
   2. юнит-тестов бизнес-логики;
   3. юнит-тестов ключевых частей;
   4. интеграционных в целом;
   5. интеграционных ключевых частей (если отличается);
   6. всех тестов вместе.
3. **После первого анализа — достижимы ли нормы покрытия** из `backend-test-rules_ru.md` по умолчанию, по каждому
   пункту: юнит-тесты в целом, бизнес-логика, ключевые части, планировщики. Не достижима или очень много работы →
   почему и рекомендация: до скольки снизить или что сделать, чтобы дойти. Обсуждаем с пользователем; снизить —
   только с его разрешения и по каждому пункту отдельно (так `1. Все тесты → 1.16` работает для покрытия).
   Результат — в первый отчёт («3. Отчёт», пункт 2), сниженные нормы — в «3. Отчёт», пункт 3.

## 3. Отчёт

Делаем на шаге 0 и в конце каждого шага из «4.1 Шаги». В имени файла отчёта — дата, в шапке — к какому шагу
или шагам он относится: `Шаг 0 — первый отчёт`, `Шаги 1, 4`. Отчёт посреди шага → в шапке, какие шаги сейчас
в процессе: `В процессе: шаги 1, 4`.

1. **Нарушения** — по каждому пункту цели: сколько, где, насколько сложно исправить и когда проверяли. Пустых клеток
   нет: значение или «—».

   | Пункт цели | Нарушений | Где | Сложность | Проверено |
   |---|---|---|---|---|
   | `backend-test-rules_ru.md → 1. Все тесты → 1.5` | 0 | — | — | 2026-11-20 |
   | `backend-test-rules_ru.md → 1. Все тесты → 1.6` | 3 | `A`, `B`, `C` | низкая | 2026-11-20 |
   | `backend-test-rules_ru.md → 2. Юнит-тесты → 2.1` | — | — | — | не проверяли |

   - **Нарушений** — число; `0` с датой — проверили, нарушений нет.
   - **Где** — ссылки на тесты (классы, файлы).
   - **Проверено** — дата проверки; не смотрели — «не проверяли».

2. **Покрытие** — те же пункты, что в анализе (этап 2): в начале и сейчас.

   | Покрытие | В начале | Сейчас |
   |---|---|---|
   | юнит-тестов в целом | 41% | 55% |
   | юнит-тестов бизнес-логики | 48% | 66% |
   | юнит-тестов ключевых частей | 52% | 78% |
   | интеграционных в целом | 30% | 44% |
   | интеграционных ключевых частей | 35% | 61% |
   | всех тестов вместе | 58% | 70% |

   Сравниваем с прошлым отчётом: упало → почему — в «Комментарий, допущение» плана шага.

   В первом отчёте ещё — достижимы ли нормы (этап 2, пункт 3):

   | Пункт цели | Норма | В начале | Не хватает | Достижима | Время с ИИ, ч | Почему, рекомендация |
   |---|---|---|---|---|---|---|
   | `backend-test-rules_ru.md → 2. Юнит-тесты → 2.1` | 60% | 50% | 1700 строк | да, без скопированных библиотек | 0 | 3000 строк — чужие библиотеки; считать без них |
   | `backend-test-rules_ru.md → 2. Юнит-тесты → 2.2` | 80% | 72% | 750 строк | да | 20 | логика в обычных сервисах — юнит-тесты с моками |

   - **Время с ИИ, ч** — сколько часов, чтобы дойти до нормы, если тесты пишет ИИ, а человек проверяет.

3. **Сниженные нормы** (этап 2, пункт 3) — если есть: какой пункт цели, было, стало, кто и когда разрешил.

   | Пункт цели | Было | Стало | Разрешено |
   |---|---|---|---|
   | `backend-test-rules_ru.md → 2. Юнит-тесты → 2.2` | 80% | 60% | <кто>, <дата> |
   | `backend-test-rules_ru.md → 1. Все тесты → 1.2` (интеграционные) | каждый параметр запроса хотя бы раз | только параметры ключевых частей | <кто>, <дата> |

## 4. План и работа

### 4.1 Шаги

**Шаг 0. Первый отчёт** — до любых правок: анализ (этап 2), достижимы ли нормы, отчёт (этап 3). Это точка отсчёта:
с ним сравниваем все следующие отчёты.

**Шаг 1. Имеющиеся тесты — в порядок.** Новых тестов не пишем.

1. **Сломанные, выключенные и нестабильные** — чиним всегда и сразу; падают время от времени — переделываем. Падение
   сборки при упавшем тесте можно включить сразу, для себя, — чтобы видеть все упавшие.
   `1. Все тесты → 1.4, 1.5, 1.12, 1.13, 1.14`.
2. **Правильность написанных:** двойные тесты — пометить для удаления; тест не своего уровня — переделать
   (недостающие тесты — в шагах 3–5); тест, который ничего не проверяет, — починить.
   `1. Все тесты → 1.1, 1.2, 1.3`.
3. **Структура:** имена и пакеты → помощники и базовые классы → файлы (SQL, CSV, JSON) → тестовые данные.
   `1. Все тесты → 1.6, 1.10 → 1.7 → 1.8, 1.9 → 1.11`.
4. **Всё остальное, что не требует новых тестов:** интеграционные — на настоящем приложении, через настоящие фильтры
   безопасности, с моками только внешних систем, на Testcontainers; планировщики в них выключены. Тесты
   сгенерированного кода и интеграционные, которые проверяют не то, — пометить для удаления.
   `2. Юнит-тесты → 2.5`, `3. Интеграционные тесты → 3.2–3.5`, `4. Планировщики → 4.1`.

**Шаг 2. Находки проверки кода** — есть отчёты GLASS WORKS или другой проверки → тест на каждую находку. Код менять
нельзя (этап 1) → тест фиксирует, как есть сейчас, находка — в список проблем проекта.

**Шаги 3–5. Юнит-тесты, интеграционные, остальные** — старые тесты приводим к правилам, недостающие дописываем до
нормы покрытия (с учётом сниженных, этап 2, пункт 3). Внутри шага — по ключевым частям, critical первыми: кончится
время — важное уже сделано. Шаг 5 — всё, что не попало в шаги 3 и 4: SQL-тесты (мапперы, репозитории),
планировщики и тому подобное.
Пункты цели: шаг 3 — `1. Все тесты → 1.2`, `2. Юнит-тесты → 2.1–2.4`; шаг 4 — `1. Все тесты → 1.2`,
`3. Интеграционные тесты → 3.1`; шаг 5 — `1. Все тесты → 1.2`, `4. Планировщики → 4.2, 4.3`.

### 4.2 Правила для всех шагов

- **Не трогаем то, что уже по правилам:** тест проходит, со временем падать не начнёт, случайно не падает и написан
  по правилам (`1. Все тесты → 1.15`).
- **Новые тесты — только по всем правилам цели и на структуре шага 1**, чтобы потом не переделывать.
- **Любой тест удаляем, только когда** его заменили нашим правильным или он стал не нужен — и покрытие после
  удаления не ниже нормы — из `backend-test-rules_ru.md` или сниженной (этап 2, пункт 3); ниже нормы →
  `1. Все тесты → 1.16`. До этого — помечаем в `project-issues.md` части, со ссылкой на строку отчёта или таблицы
  плана, где сказано почему; не `@Disabled` (иначе нарушим `1. Все тесты → 1.5`). Удаляем перед сборкой и
  коммитом. Сломанные и выключенные не помечаем, а чиним сразу (шаг 1).

  | Тест | Почему (ссылка) | Чем заменён | Удалён |
  |---|---|---|---|
  | `<пакет>.ATest.method` | `tests/backend-report-<ГГГГ-ММ-ДД>.md` → `2. Юнит-тесты → 2.5`: проверяет сгенерированный код | — | [ ] |

- **Конец шага:** полная сборка с покрытием → покрытие не упало (упало → объяснить и обосновать в «Комментарий,
  допущение») → отчёт (этап 3) → коммит.
- **Шаг большой → промежуточные коммиты.** Коммит в конце шага — обязательно с проверкой покрытия.
- **В коммите все тесты зелёные.** Ни одного упавшего теста в коммите.
- **Пункт цели не выполнить или очень сложно** → в «Комментарий, допущение» — почему, и подтвердить у пользователя
  (`1. Все тесты → 1.16`).

### 4.3 Таблица плана

Составляем на каждый большой шаг из «4.1 Шаги» — до его начала, ведём в процессе. Строки — что делаем в этом шаге,
подстроки — `1.1`, `1.2`; у подстроки цель и числа не пишем — они у строки.

План шага 1 «Имеющиеся тесты — в порядок»:

| Готово | # | Что делаем | Цель | Оценка, ч | Тестов затронет | Файлов всего | Комментарий, допущение |
|---|---|---|---|---|---|---|---|
| [ ] | 1 | Сломанные, выключенные и нестабильные — починить | `backend-test-rules_ru.md → 1. Все тесты → 1.4, 1.5, 1.12–1.14` | 4 | 10 | 2 | |
| [x] | 1.1 | `ATest` — на подменяемых часах | | | | | |
| [ ] | 1.2 | `BITest` — не зависит от порядка запуска | | | | | |
| [ ] | 2 | Двойные тесты — пометить для удаления | `backend-test-rules_ru.md → 1. Все тесты → 1.1` | 2 | 14 | 9 | 2 теста остаются: старый формат файла ещё принимается, разрешено (решение от <дата>) |

- `[x]` — закоммичено и полная сборка зелёная; строка с подстроками — когда готовы все её подстроки. Шаг готов
  целиком — когда готовы все строки и покрытие проверено («4.2 Правила для всех шагов» → «Конец шага»).
- **Оценка, ч** — до начала шага: объём виден заранее, а не на середине.
- **Комментарий, допущение** — где шаг отступает от цели: от какого пункта, сколько тестов, почему; разрешено ли —
  «разрешено (решение от <дата>)»; что ещё нужно согласовать. Сказать нечего — пусто.

## 5. Когда закончили

Стандартный отчёт (этап 3) — после последнего шага.
